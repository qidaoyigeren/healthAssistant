# material-review@2 覆盖保证与完整交付 —— 设计决策（2026-09-13）

**这份文件约束本轮实现，不描述过程。** 上一轮的架构（契约、状态模型、领域工具、
统一推进核心、证据关联、报告版本、增量更新）**不动**，本轮只补它的四个缺口：

1. 必须覆盖的材料仍依赖模型逐条选择，真实任务只读一条就停止；
2. 补问创建后没有清楚的等待边界，模型继续重复提问；
3. 部分交付、工程检查通过与用户目标完成容易混淆；
4. 材料补充、事实确认与权威记录修改没有明确区分。

以前三条的共同根因是同一个：**把"运行器的数据准备"和"模型的调查策略"混在了一层。**
本轮把它们分开，并让报告与界面说得出谁做了什么。

---

## 0. 一句话

基础材料覆盖是**运行器**的职责，不是一个工具调用；模型只做语义调查。

---

## 1. 两个职责层

| | A. 基础材料覆盖（运行器） | B. 语义调查（模型） |
|---|---|---|
| 谁做 | 代码 | 模型 |
| 做什么 | 枚举选中的材料与要比较的记录；在既有权限路径下实际读取；校验完整性；取出字段与来源位置；执行**现有**确定性字段比较；给出处置（covered / unreadable / unmatched / insufficient） | 哪些差异值得解释；还要核对什么时间/对象/条件；真正必要的补充是什么；是否查其他来源；新证据下判断怎么改；就诊准备怎么组织 |
| 记在哪 | `state.source_reads` + `state.material_items[ref].comparison` + `coverage_requirements[].disposition` | `state.questions/findings/assertions/research_decisions` |
| 花不花模型预算 | **不花**（不产生规划调用） | 花 |

**为什么这不会把系统工作冒充成模型能力。** 三条不可越过的线：

* **归因分开**：读取凭据记住是谁读的（`system_read` / `model_requested_read`），
  `material_read_refs` **只**记模型读过的条目。报告与页面同时给出 `system_material_refs`
  与 `model_material_refs`，并且写明"系统读取支撑的是确定性字段比较"。
* **结论分层**：系统落成的发现 `origin=system`，是对材料与记录的**字段比对**；
  模型的解释仍要过 `verify` 的三档核查，语义档只给"需人工确认"，从不给 supported。
* **参与分账**：`attribution` 里 system / model / unattributed 三段各自列清。模型这一版
  一轮都没参与时，交付**不允许**是 complete，报告首页写明"这一版没有模型参与"。

---

## 2. 覆盖不能停在 pending

`coverage_requirements` 的每一条都必须有处置，而处置**不取决于模型**：

* `covered` —— 实际读过、通过校验、并得到了确定性结论；
* `unreadable` —— 打不开或未通过完整性校验；
* `unmatched` —— 读得到，但没有可比较的对象；
* `insufficient` —— 读到了，但字段不足或依据不足，**必须带具体原因**，并且**必须
  有一条待确认的问题或补充请求在跟进它**（否则交付检查报
  `uncertainty_without_basis`）。这一条正是"把所有 pending 改成 insufficient 换
  complete"的止点。

有界性：一趟最多处理 `COVERAGE_BATCH` 条，一条原文按 `PAGE_CHARS` 分页、一条最多
`MAX_PAGES_PER_ITEM` 页；一趟没处理完的**明确记为未处理**，下一趟从保存的 offset
继续。页位置在**读完整条**之后才清除，部分读取**不落发现、不记账**——半句话不能当
整条材料的结论。

材料改版 / 记录改版后，指纹变了的条目重新读取，其余条目跳过；`read_credential()`
比对指纹，因此旧版本的读取凭据自动作废，凭它得出的结论不会继续成立。

---

## 3. 补问是一个状态转换

`request_information` 成功之后不再是一个普通工具调用：

1. 先跑完与补问无关的确定性覆盖（不花模型调用）；
2. 若**没有剩下任何需要判断的事**（覆盖全部有处置，且每条还开着的问题都被某条未
   回答的补充请求挡着），立即进入 `waiting_input` 并结束本轮；
3. 还有可独立推进的工作时照常继续，并记录这次暂停。

请求身份 = **任务 + 对象 + 待补字段**（不含自然语言原句、不含关联问题）。

* 换个措辞问同一件事 → 同一条请求（关联问题与字段在复用时合并）；
* 同一对象的**不相交**字段 → 两条请求（合并了，另一个字段永远等不到答案）；
* 说不清对象的请求 → 明确拒绝并说明理由，**不**推测应该写进哪条患者记录。

回答也一样：只有被实际回答到的请求被关闭。只答了一部分，其余仍然开放。

## 4. 三类输入不互相冒充

| 输入 | 走哪条路 | 结果 |
|---|---|---|
| A. 材料说明 | `answers[]`（`kind=material_note`） | 记成"材料上写的是什么"，参与比较但**标明来源是用户说明**；不改当前记录 |
| B. 用户陈述 | `answers[]`（`kind=user_report`）/ `semantic` | 记成"按报告记录"，核实状态 `recorded_as_reported`；不改当前记录 |
| C. 权威记录更新 | 既有的受控写入路径（`medications`） | 真的改当前记录，留下原值 → 新值与来源 |

前端里"保存补充"只发 A/B；要改记录必须在对应请求上**逐条勾选确认**，才发 C。
报告的"依据"一节把三者分开写：`依据（材料）` / `依据（当前记录）` / `依据（您的补充）`。

---

## 5. 交付状态的三条轴，重新对齐含义

`run` / `delivery` / `evidence` 三条轴继续独立，但本轮的交付语义收紧了两处：

* **有未回答的补充请求，或还有没查完的问题 → `delivery=partial`。**
  报告本身可以是完整的（它准确地写出还剩什么没定），但用户要的那件事还没交付完。
  "报告生成好了"与"任务完成了"不是同一句话。
* **这一版没有模型参与 → 交付不得为 complete**（`model_not_consulted`），
  并且报告与页面都写明确定性部分已完成、语义部分未处理。

两类缺口都是**非阻塞**的：它们让交付降级为"部分"，但不让模型陷在无法满足的循环里。
