# P3：跨会话待办与就诊准备

`stage0/care_tasks.py` 保存任务契约、患者基线、状态、缺失项、处理记录、后台 run 引用及预算。材料核对契约 v2、当前药单与就诊摘要契约 v1。完成由代码校验已保存产物和后台检查状态，不能通过请求指定 `completed`。

等待输入与等待专业审核是不同状态。补充操作携带任务身份及 revision，并与候选更正/确认共用原子事务；同键补充不重复执行，旧 task revision 被拒绝。事实变化要求重新核对；临床决定继续由现有 review/outbox 处理，待办不代替审核。`due_at` 仅是应用内计划时间，没有新增应用关闭后的主动通知。

预算包含最多 64 个确定性处理步骤。材料任务还固定总资源上限：1,000,000 token 准入单位、256 次模型外呼；每次创建后台检查前预留该 run 的最大 token/call 预算，并将预算保存进既有 workflow run，重启不能重置。预留保守地不回收；已知实际用量从原 run 账本汇总，未知用量保留未知。已有任务的材料操作不能脱离任务身份绕过预算。取消停止后续任务处理，已提交药单和回执保留。

总览、助手均有待办入口，`/tasks` 可继续处理和生成摘要。摘要保存生成时的患者 revision、当前报告药单、近期 30 条事件、用户报告事实、未核实材料及来源；HTML/Markdown 为不可变产物，后续事实变化时列表标记需更新。

API：`GET/POST /v1/care-tasks`、`POST /v1/care-tasks/{id}/resume`、`GET /v1/visit-summaries`、`GET /v1/visit-summaries/{id}/download?format=html`。明确的药单事件走确定性规划，开放问题继续使用既有 planner；仅含相关关键词的歧义自然语言不会误走快捷路径。

验证：任务竞争、重复恢复、累计预算、取消效果保留、审核等待和事实过期、后台实际执行及摘要下载，见对应测试和最终浏览器工件。任务列表通过打开页面/补充事件/手动继续恢复，不宣称独立主动调度。
