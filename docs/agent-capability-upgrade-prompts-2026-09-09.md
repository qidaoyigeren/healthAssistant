# HealthAssistant：Agent 决策能力升级实施 Prompt

本文是实施任务说明，不代表功能已经完成。五项能力对应：A1 信息缺口驱动规划、A2 开放任务持续执行、A3 自适应运行、A4 受限多 Agent、A0/A5 能力评测。

建议顺序：A0 → A1 → A2 → A3 → A5。A4 是可选实验，若执行，放在 A3 后，并纳入 A5 对比。第一轮执行 A0–A1，获得基线和一条可运行的能力链路。各阶段不得以未来阶段尚未实施为由留下本阶段应完成的接入。

```text
本轮执行范围：A0–A1。

目标：在现有时序记忆、工具运行时、证据存储、任务与恢复机制上，实现信息缺口驱动规划，并为它建立可复现基线。直接完成所选范围的代码、适用迁移、API、前端接入、必要测试和实施报告，不要停在方案或骨架。

以当前代码为准确认哪些能力已存在，复用后补齐增量。保留工作区已有修改、正式患者库与历史报告。先简要报告现状和执行顺序，然后持续完成本轮已授权工作；常规实现选择自行判断，不重复请求确认。

不自动执行本文未选阶段，不新增定时任务、不发布部署。真实模型实验遵守已有的数据范围、供应商和预算授权；缺少必要条件时记录 unavailable，并完成全部独立的本地工作，不将缺少真实模型验收改写为通过。
```

后续复用启动 Prompt，将“本轮执行范围”替换为 A2、A3、A4 或 A5，并同步将目标句改成对应阶段目标。也可一次指定 A0–A3、A5；A4 必须明确选择才执行。以下各阶段正文均可作为“遵守本文通用约束，执行以下任务”的独立实施 Prompt。

## 所有阶段的通用约束

1. 当前实现优先于历史规划。重点入口：`stage0/agent.py`、`graph_runner.py`、`memory.py`、`care_tasks.py`、`evidence_quality.py`、`ddi_engine.py`、`server.py`、`stage0/harness/`、`stage0/product_evals/` 与 `frontend/src/`。先确认路径和实际调用链，不照搬历史行号。
2. 已有能力包括版本化事实、选择性结论失效、重查、预算、幂等回执、outbox、LangGraph 恢复、人工审核、证据回读、固定照护任务。不要重复造这些底座，不整体重写 agent.py 或 memory.py，不因功能命名引入新框架或图数据库。
3. 保留默认本地确定性路径；新增模型能力显式启用。开关关闭时旧功能可用，已有新任务要明确可读取、可恢复还是需要迁移，不能静默切换执行版本。模式必须真实标明 deterministic、scripted 或 llm。
4. 新增持久状态必须有 scope、版本与迁移语义。所有领域写入经过已有权限、事实新鲜度、策略、回执和审计；模型不能生成权威版本号、伪造证据或确认回执。保持单写者和当前事务约束，外部模型请求不能持有数据库写事务。
5. 未确认材料、用户报告、已验证事实、通用说明书和推导结论分开。未列出某药不能推断停药；缺少证据不能推断无风险。用户确认记录内容不是临床审批。延续现有医疗输出边界和最终响应检查。
6. 复用 EvidenceStore 的授权与内容完整性检查。上传文本、引用和 worker 结果都作为数据，不能改变系统权限、预算、目标或完成条件。持久化可核验的决策摘要与引用，不要求或记录模型隐藏思维链。
7. 调试、迁移与故障注入使用隔离数据库和明确标注的合成患者。保留当前未提交修改和历史验收工件。检查点恢复不得重置累计预算，取消不得删除已经提交的领域效果。
8. 只在涉及真实业务不变量、错误恢复和模型决策边界时增加有意义的测试；不为简单展示变更创建镜像测试。运行与改动相关的后端检查；涉及前端则执行类型检查、构建及真实浏览器关键流程验证。
9. 真实模型调用遵守现有 opt-in 与预算。发现密钥不等于新付费或新供应商授权，不打印凭据。已有授权可复用；确实缺少必要授权时只提出一次具体问题，继续不依赖它的工作。不得用脚本响应冒充真实模型实验。
10. 每阶段产出 `docs/agent-capability-upgrade/Ax/implementation-report.md` 和结构化验收结果，记录代码版本/工作区差异指纹、配置、数据划分、实际命令、结果、限制。不得预填提升比例，缺少验证标记 unavailable；只完成工程门禁时明确说明范围。

## A0：建立 Agent 能力基线与评测协议

```text
执行 A0：为后续规划、持续任务和运行时改造建立基线，暂不改变 Agent 决策行为。

现状核实：
- 区分既有 DDI、记忆、Harness、产品流程评测，不将产品 held-out 为空解释为全仓库没有 held-out。
- 查看最新真实调用报告，确认 provider 错误、模型输出校验失败和任务未完成分别如何记录。
- 查看现有 traces、manifest、usage、operation receipts，尽可能复用。

实施要求：
1. 定义 Agent 任务样本格式，至少包含 task_id、family_id、输入事件序列、初始状态、可用材料、预期缺口、必要产物、允许的等待状态、关键禁止结果和预算。不要规定唯一工具调用顺序。
2. 建立一个紧凑开发集，覆盖：信息完整、缺药名/单位/日期、材料冲突、适用条件缺失、重复检索、中途重启、等待期间事实变化、工具超时、模型限流、取消与重复提交。先保证每类有代表样例，样本数如实报告。
3. 准备 baseline 配置与回放输入。即使后续代码改变，也能通过固定 revision、隔离工作树或保留旧策略适配器重跑基线；不只保存一个无法复现的总分。
4. 接入两种评测路径：固定工具结果回放用于定位规划差异；真实工具端到端用于检查整体能力。脚本 planner 的测试只计工程回放。
5. 区分 execution_status、goal_status、answer_status 或等价独立字段。保留旧 API 兼容；业务事件保存成功、有效回答、任务完成不能互相替代。模板正确完成精确查询可以算任务成功，不能计作 LLM 回答成功。
6. 定义评分：必要提问召回、无效提问数、受证据支持的 claim 比例、错误完成、任务最终状态、恢复成功、重复效果、模型/工具调用数、真实 token、延迟和降级原因。说明分母、不可评分样例及 unknown usage。
7. 为独立 held-out 建立收集与封存协议，按情景家族和材料来源隔离；同义改写不算独立样本。作者用于开发的合成集不得宣称独立盲测。缺少独立数据就标记 unavailable。

验收：
- 内置一个应失败的样例证明评分器能失败；缺数据不能整体 pass。
- 当前实现跑出可复现的实际基线，并保留失败轨迹。
- 交付统一命令、样本格式说明和后续阶段对比方式。
```

## A1：信息缺口驱动规划与证据覆盖检查

```text
执行 A1：将开放问题的规划升级为“待证问题 → 缺口 → 动作 → 验证进展”，复用现有单动作 planner、工具运行时和安全边界。

先确认 agent.py 的 _reflect、planner proposal schema、策略守卫、上下文序列化、最终回答，以及 evidence_quality.py 的 assess_claim、bounded_research 的实际接入。已有词法支持筛查与有界搜索要保留并扩展。

实施要求：
1. 定义可序列化的 InvestigationState 或等价对象。至少包含目标、患者版本、待证 claim、支持/反对证据引用、缺失事实、未覆盖检查项、下一步候选和终止原因。覆盖范围来自版本化任务契约，模型可提出新增问题，但不能删除代码要求的必查项。
2. 区分患者事实缺失、证据缺失、证据冲突、工具失败和来源失效。缺失事实先查现有权威记忆，确实没有再提问；存在冲突不能通过让用户随意选择一个答案消除。
3. 为 planner 工具提案增加解决哪个 gap、预期获得什么可观察结果的结构化关联，兼容现有 schema 与恢复数据。模型负责提出动作，代码核验 gap 引用、工具权限、输入和结果来源。
4. 工具返回后更新 gap 状态。新增重复 chunk、重复调用或无依据改写不能算进展；以新增有效证据、已核实字段、明确冲突或真实回执衡量进展。
5. 对低置信度和条件不足做针对性补检索。保留 supported / contradicted / insufficient，并增加来源和条件状态；先实现可检查的实体、时间、否定、适用条件规则。若增加模型语义核查，要独立开关、结构化输出并校验引用；模型自报高置信度不能覆盖硬规则。
6. 加入有界停止：必查项完成、等待用户、等待审核、无进展、预算不足和不可恢复失败。unknown/insufficient 必须进入最终产物；满足“交付有界核查报告”不等于“证明没有风险”。
7. 按问题装配上下文：固定保留目标、权威版本、关键事实状态、相关未决冲突和缺口；证据正文按需回读。保留完整性标记，安全检查读取完整权威集合，不能只靠相关性截断。
8. 接入真实开放问答路径、持久检查点和已有结果 bundle；文字、卡片与结构化状态共享数据来源。前端显示已核查范围、待补充内容和终止原因，并可回读证据。状态更新不得与事实写入重复执行。

验收：
- 已有答案的事实不再重复询问；缺少关键事实时能等待输入。
- 引用存在但条件不符时仍为 insufficient；反对证据不被吞掉。
- 同一查询或同一结果反复出现时能有界停止。
- 工具失败、预算耗尽不能清空既有警告或宣称完整检查。
- 改造前后使用同一开发集比较质量、调用量和延迟；如尚无真实模型结果，明确只通过工程回放。

交付一条可演示的完整链路：开放问题 → 发现缺口 → 定向读取/搜索/提问 → 校验覆盖 → 带证据和剩余缺口的回答。
```

## A2：开放目标的持久化与增量重规划

```text
执行 A2：在现有 CareTasks、LangGraph、outbox 和操作回执上，支持跨会话持续完成开放核查目标。

当前固定契约支持 reconcile_material、current_medications、visit_summary。新增一种边界清楚的开放契约，例如 evidence_review，第一版限定“围绕已有患者记录与材料进行证据核查并整理待确认问题”，避免建设通用任意目标平台。

实施要求：
1. 新任务保存目标版本、子目标及依赖、所需输入、证据/事实版本、子目标结果引用、gap 状态、run 关联和任务级累计资源。子目标可以由模型提议，代码检查契约、数量上限、循环依赖、允许工具与完成条件。
2. 保留 ready/running/waiting_input/waiting_review/completed/failed/cancelled 或兼容状态机。区分“产出一份说明证据不足的报告”和“完整核查已完成”，完成由契约与持久产物判定，不接受模型直接写 completed。
3. 等待输入时保存具体问题与 gap/subgoal 关联。用户可在现有任务界面补充，也能通过携带 task_id 的后续对话继续；存在多个可能任务时不可猜测归属。复用现有输入确认和受控领域写入路径。
4. 恢复先检查患者、材料、来源、契约和执行版本。复用有效步骤，失效对应依赖及其下游；无法可靠判断依赖时采用保守重查并记录原因。已有待审决定继续遵守新鲜度校验。
5. 多个新 run 共享任务预算，检查点恢复和用户重复提交都不能重置预算。等待不持有 worker lease、线程或事务；使用既有恢复队列和去重语义。
6. 处理等待输入与取消同时发生、重复继续、崩溃发生在领域提交后但 checkpoint 前、旧任务版本恢复等情况。复用回执和版本检查，不额外造另一套提交协议。
7. 扩展任务 UI：展示子目标、等待原因、可补充字段、恢复后的重做范围、实际结果引用和取消。明确已保存的领域效果会保留。

验收演示：
- 合成开放核查任务在缺材料时等待；关闭并重启服务后继续同一任务。
- 等待期间修改一项相关事实与一项无关事实，核验选择性失效以及未受影响产物的复用。
- 重复继续和提交后崩溃恢复不产生重复领域效果。
- 最终产物与完成状态一致，预算跨多个 run 累计。

复用 A0/A1 的评分和状态语义。若前置能力未完整接入，先补齐本阶段必需的最小依赖并报告，不能静态模拟长期执行。
```

## A3：任务路由、预算分配和失败恢复

```text
执行 A3：降低不必要的模型调用，并提高真实任务在延迟和供应商故障下的可完成性。

先复核最新真实调用报告与当前超时、预算账本、SDK 重试、熔断、批处理和降级实现。已有能力先测量再改，不能只扩大超时或切换模型来声称架构提升。

实施要求：
1. 明确三种路径：精确权威查询、固定契约流程、信息缺口驱动的开放规划。显式 API 类型可确定性路由；自然语言复合请求和歧义请求不能因命中“药单”等关键词而丢弃其余目标。响应记录 route 与简短可核验的依据。
2. 规划工具按所选契约收敛，独立只读查询优先复用已有批处理。批处理和并发分开定义；部分失败保留成功结果，写操作不因合批绕开既有顺序和事务边界。
3. 在总预算内分配规划、工具、验证和发布阶段预算，提前预留最低收尾资源。预留、实际消耗、未返回 usage 的估算分开记录；任何预留调整都不得凭空增加总额度。
4. 利用 task/gap 状态与结果指纹避免无意义再规划。确定性判定可以直接推进的步骤由代码执行；存在新证据、冲突或未预见缺口时交给 planner。
5. 分类处理参数校验、429/暂时性故障、超时、无证据、永久失败和 effect_unknown。重试限次数且受剩余 deadline、幂等性和原供应商策略约束；不要叠加 SDK 与应用层重试造成放大。持久等待用现有队列，不让唯一 worker 睡眠占用服务。
6. 保持 execution/goal/answer 状态分离，明确保存了什么、未检查什么、结果是否可继续。模板正确完成确定性目标可算成功；失败的开放回答不得仅凭业务事件已保存而计为完成。
7. 可配置的供应商路由若已有则复用；新增供应商或扩大付费调用必须服从用户明确授权，不默认执行。供应商整体不可用属于环境限制，算法不能保证消除限流。

验收：
- 比较相同模型、材料、初始状态和总预算下的 baseline 与改进配置。
- 覆盖复合请求误路由、批处理部分失败、模型限流、收尾预算不足、重试恢复和取消。
- 报告任务质量、p50/p95（附样本量）、模型/工具调用量、token、降级率和失败原因。
- 同时报告 provider 健康时的决策表现与故障注入下的恢复表现；不能把快速失败当有效提速。
- 设置事先约定的质量非劣门槛，速度提升不能掩盖必要检查遗漏。
```

## A4：可选的证据收集与独立核查多 Agent 实验

```text
执行 A4：在现有只读委派机制上实现可关闭的真实模型 worker 实验，验证是否比单 Agent 和批处理有增量价值。

当前 harness/delegation.py 的 worker 是确定性只读流水线。保留该模式的真实命名和兼容行为；未进行模型规划的 worker 不能包装为自主 Agent。

实施要求：
1. 只允许两个固定角色：evidence_researcher 负责提出检索动作、收集支持与反对证据；evidence_checker 负责独立读取原文、核查实体、否定、适用条件、日期和版本。worker 在受限预算内进行真实的工具选择与停止决策，不能只是模型改写固定流水线结果。
2. 主协调器管理目标、任务分配、总预算、结果合并与最终提交；worker 不拥有领域写入或审核权限，不允许递归委派、扩大 scope、修改契约或调用未授权工具。
3. checker 应获得待证 claim、必要事实版本与原始证据引用，避免直接复制 researcher 的完整论证。独立上下文只是核查设计，不意味着统计独立或保证正确。
4. 返回结构化结果：claim_id、verdict、evidence_refs、条件、缺口、错误和 usage。父 Agent 重新校验引用、scope、内容哈希和事实版本；冲突不能通过模型投票或取平均置信度消除。
5. parent 与所有 worker 的实际/预留/未知 usage 均进入同一任务账本，统一取消、超时、派发上限与恢复语义。若并行需要改预算记账，先证明不会超售；不把同步委派标成并发加速。
6. 仅在复杂材料或证据冲突达到可解释触发条件时启用；简单任务走已有路径。所有结果标明 worker_kind 与实际模型，默认保持关闭。
```
