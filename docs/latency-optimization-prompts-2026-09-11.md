# HealthAssistant：规划延迟优化实施 Prompt

本文是实施任务说明，不代表优化已经完成。背景：2026-09-11 的坐标批次在新端点（TokenDance `glm-5.3-flash`）上首次达成无兜底自主规划门槛（3/3、供应商响应 9/9、限流 0），但**每回合 72 秒**，单次规划 **21.9 秒**中位数。可用性已解决，延迟成为当前主要产品问题。

**已有实测结论，不要重新推导，也不要推翻前先看数据**（[latency-2026-09-11/latency.json](agent-capability-upgrade/latency-2026-09-11/latency.json)）：

| 端点 / 场景 | 输入 token | **输出 token** | 延迟 |
|---|---|---|---|
| Zhipu · 真实载荷 | 4224 | **49** | **1.5 s** |
| TokenDance · 极小提示（437 tok） | 437 | **1451** | **40.4 s** |
| TokenDance · 真实载荷 | 4219 | **1162** | **31.6 s** |
| TokenDance · 不设 `thinking:disabled` | 4219 | **2440** | **55.9 s** |

三条已确证的结论：

1. **延迟由输出 token 决定（≈27 ms/token），与输入规模基本无关。** 极小提示比重载荷更慢，因此**载荷瘦身不是有效方向**。
2. **`thinking: disabled` 有效但未被真正遵守**：2440 → 1162，而 Zhipu 在同样设置下只有 49。
3. 同一协议在 Zhipu 上 **1.5 s/调用、参数拒绝 0**——慢不是协议问题。

## 通用约束

1. **当前实现优先于本文。** 重点入口：`stage0/agent.py`、`turn_budget.py`、`extract_ddi.py`、`stage0/source_fingerprint.py`、`scripts/model-qualification-probe.py`、`scripts/latency-diagnostic.py`、`scripts/run-planner-live-acceptance-v3.py`。先确认实际调用链，不照搬本文行号。
2. **不整体重写 `agent.py` 或 `memory.py`。** 不因优化引入新框架、新调度器或新依赖。
3. **协议语义零放松。** 安全校验、证据回读、终止条件、权限、幂等与事务原子性、重启后累计预算，一律不改。优化不得以降低这些为代价。
4. **先测量，再改动，再测量。** 任何延迟改动都要有改前/改后同一度量口径的数字；没有测量就如实写"未测量"，不得写成推定收益。
5. **一次只动一个变量。** 上一轮切换端点时同时变了四项配置，虽然最终因重试从未触发而侥幸归因干净，**不能依赖这种运气**。对照必须可控，或明确声明不可控。
6. **真实模型调用遵守既有 opt-in 与预算。** 不打印凭据；发现密钥不等于新供应商授权。新增端点的授权要显式加入 `AUTHORIZED_LIVE_TARGETS` 白名单，不许绕过。
7. **不使用 `max_tokens` 硬截断来"变快"。** 它会在推理中途截断，产出无效 tool call，把延迟问题换成参数拒绝问题。
8. 调试与故障注入使用隔离数据库和明确标注的合成患者。检查点恢复不得重置累计预算，取消不得删除已提交的领域效果。
9. 只在涉及真实业务不变量、错误恢复和模型决策边界时增加有意义的测试；不为展示变更创建镜像测试。
10. 每阶段产出 `docs/agent-capability-upgrade/latency-2026-09-11/Lx/implementation-report.md` 与结构化验收结果，记录源码指纹（用 `stage0/source_fingerprint.py` 的 `repo` 作用域）、配置、实际命令、结果、限制。

## L0：建立延迟度量与基线

```text
执行 L0：把"延迟"变成可复现的度量，暂不改变任何规划行为。

现状核实：
- 阅读 scripts/latency-diagnostic.py，确认它已能分别记录 prompt_tokens、completion_tokens 与墙钟延迟。
- 阅读 scripts/analyze-planner-metrics.py，确认现有逐次指标里延迟字段的口径（planner_latency_ms_each / wall_ms）。
- 确认 stage0/turn_budget.py 是否已记录每次调用的 token 明细；如只有总量，说明缺口。

实施要求：
1. 定义延迟度量口径并在产物中落地：每次调用的 prompt_tokens、completion_tokens、墙钟延迟，以及每回合的调用数与总墙钟。说明分母与不可评分样例。
2. 把 completion_tokens 确立为延迟的第一预测指标；在度量中直接给出"延迟/输出 token"比率，避免后续只看总延迟。
3. 对既有三个批次（planner-closeout-2026-09-11、planner-closeout-v3-2026-09-11、provider-switch-2026-09-11）统一重算该口径，形成可比基线。旧产物缺字段就如实标 unavailable，不得回填估算值。
4. 区分四种耗时：供应商排队、模型 prefill、模型 decode、本地工具执行。用已有数据说明当前各项占比，缺证据的部分标记为推断。
5. 不要把"首次可见反馈"与"最终结果"混为一谈；交互反馈与批次墙钟是不同测量，分别记录。

验收：
- 一条命令能从既有产物重算基线，且复现本文给出的数字或明确报告差异。
- 度量能指出一次具体调用的 token 明细，而不只是总量。
- 交付口径说明与后续阶段的对比方式。
```

## L1：按输出 token 纪律选型

```text
执行 L1：筛选并验证一个输出 token 纪律良好的规划端点。

现状核实：
- 阅读 scripts/model-qualification-probe.py：它当前只验证契约合规（tool_choice、具名函数、必填嵌套参数），不度量输出规模。
- 阅读 stage0/extract_ddi.py 的 AUTHORIZED_LIVE_TARGETS 与 LLM_PROVIDER 选择器，确认新增端点的授权路径。
- 复用 L0 的度量口径，不另建一套。

实施要求：
1. 扩展 qualify 探针：在同一份 v3 契约下，记录每个候选的 completion_tokens 与延迟；契约不合规的候选直接淘汰，不进入比较。
2. 候选范围限于已配置凭据的端点；新增供应商或付费档位必须显式授权，不得自行开通。缺少可用候选时如实报告，不硬凑。
3. 设立明确阈值：同一契约下 completion_tokens 应接近单次工具调用所需（参考 Zhipu 实测 49）。给出阈值依据，不事后挑选好看的阈值。
4. 对每个候选至少 3 次采样，报告每次原始值而非只给中位数；样本不足时标注不确定。
5. 选定端点后，验证它在真实批次路径（不是探针）上仍然遵守契约：参数拒绝、解析失败、代码代填必须保持为 0。
6. 记录端点、模型、实测 token 与延迟，并说明选择理由。若没有候选达标，明确给出"未找到"的结论与下一步所需条件。

验收：
- 每个候选都有同一口径的 token 与延迟数字，含原始样本。
- 达标候选在真实路径上跑出与探针一致的契约合规。
- 未达标或未测量的情况明确标注，不用探针结果冒充批次结论。
```

## L2：双端点路由（可选，仅在 L1 无达标候选或需保可用性时执行）

```text
执行 L2：在不放松协议的前提下，用主/备端点兼顾速度与可用性。

现状核实：
- 确认 429 的处理路径与"确定性拒绝不消耗调用预算"的现有实现（turn_budget.py 的 refund 语义）。
- 确认切换必须可观测：trace 与指标里要能看出本次用的是哪个端点。

实施要求：
1. 主端点优先；主端点确定性拒绝或不可用时切备用。切换原因、发生时机、切换次数必须进入 trace 与逐次指标。
2. 备用端点必须同样在白名单内且通过契约资格验证；不得为了可用性引入未验证端点。
3. 切换不得改变预算语义、不得重复计费、不得让同一逻辑调用产生两次领域写入。
4. 明确超时与放弃条件，避免"主端点慢 + 备用端点慢"叠加成更差的回合。
5. 对照实验必须可控：主/备各跑一次同配置批次，或明确声明归因不可控。

验收：
- 指标能回答"这一回合用了哪个端点、切换了几次、为什么"。
- 幂等、事务原子性、重启后累计预算的既有回归全部通过。
- 分别报告主端点、备用端点与切换情形下的延迟与可用性。
```

## L3：减少规划调用数（需要协议变更，默认不执行）

```text
执行 L3 前必须先说明为什么 L1/L2 不足，并取得明确授权。

背景：当前每回合 3 次串行规划调用（authority → 检索 → 证据回读），每次约 30 秒。仓库已有 batch_read（Harness P3，默认关闭），可在一次规划决策内执行多个纯读工具。

实施要求：
1. 先确认 batch_read 与调查契约的 allowed_tools、证据捕获、gap 推进的实际接入点，不假设它能直接用于该契约。
2. 任何合并都会改变语义：检索 query 目前是在读过权威快照之后才确定的，合并会丢掉这个依赖。必须证明该依赖在本任务族上不成立，或保留它。
3. 不得通过减少必要的安全步骤（authority 读取、证据回读）来省调用；省略必须由证据支持，不是由延迟驱动。
4. 逐次报告调用数、每次调用的 token 与延迟，以及任务结果是否退化。

验收：
- 调用数下降有明确数字，且任务结果、参数拒绝、代码代填、重复写入均未退化。
- 若语义被改变，明确写出改变了什么、为什么可接受、如何回退。
```

## 明确不做（已被数据否定，不要再来一遍）

1. **载荷瘦身 / 删除 `tool_catalog` 与 `tool_functions` 的重复** —— 输入不是瓶颈。极小提示（437 token）比重载荷（4219 token）更慢。这条曾经看起来最直观，实测无效；重做只会浪费时间。
2. **`max_tokens` 硬截断** —— 会在推理中途截断，把延迟问题换成参数拒绝问题。
3. **并行化工具调用** —— 协议上是串行依赖。
4. **用延迟更低的断言替代测量** —— 上一轮的教训是：探针中位数（10.8 s）与真实批次（21.9 s）差一倍，因为真实载荷不同。任何延迟结论必须来自真实路径或说明口径差异。
