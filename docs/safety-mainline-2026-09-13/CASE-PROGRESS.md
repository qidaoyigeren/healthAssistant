# 长期用药安全事项的持续推进（第一轮闭环，2026-09-13）

上一轮把主线立起来了（[DECISION.md](DECISION.md) / [RESULT.md](RESULT.md)）。
这一轮让它**真的能推进一件事**：Agent 拿到事项上下文、选择有意义的下一步、
补问与回答形成闭环、处置只在明确条件下成立。

**成功标准不是工具调用数或报告字数**，而是：用户补充前后，同一件安全事项发生了
可解释、可追溯的有效推进。

---

## 1. 先核实：五个已发现的设计缺口，全部在实际调用链上确认

| # | 缺口 | 确认结果 |
|---|---|---|
| 1 | `_execute_safety_case` 没有显式的事项上下文参数 | **成立**：只把一段 `goal` 字符串交给 `run_open_review`，planner 看不到"为什么有这件事/已知什么/上次做了什么" |
| 2 | 关闭校验没证明结论支持关闭 | **成立**：`_verify_conclusion_refs` 只查 `status='current'` 与版本一致。一条**风险仍在**的结论照样能关闭事项 |
| 3 | 专业复核依据只查 `applied` | **成立**：不查事项关联、不查适用版本、不查决定语义，也**不查来源是不是真的专业人员**（本项目根本没有连接真实医护服务） |
| 4 | `apply_input` 只按 request_id 标记 answered | **成立**：空值也把请求标成已答；「不知道」和"答了"没有区别 |
| 5 | `monitoring` 与其他非关闭动作一起进入等待专业复核 | **成立**：`DISPOSITION_MONITORING` 落进同一个 `else` 分支，变成 `awaiting_professional` + "已提交专业复核，等待结论" |

另外两处是同一条链上**新发现**的真缺陷：

- **`actor` 取自请求体**（`body.get('actor') or 'caregiver'`）。任何客户端都能自称复核者。
- **必要检查去重吞掉了"回到曾经检查过的状态"**：`{甲,乙} → {甲} → {甲,乙}`，集合哈希与第一次
  相同，`ON CONFLICT DO NOTHING` 让这一轮检查根本不再执行。中间那次变化产生的任何结论
  都不会被重新核对——正是"事件去重不得吞掉新的必要安全提示"要防的事。

还有一处跨会话断点：**事实被撤回后无法重新上报**。`_write_semantic_fact_tx` 用"当前行版本 + 1"
算新版本，撤回后没有 active 行 → 算出 v1 → 撞上已有的 v1。跨会话复核走到这里就断了。

## 2. 处置语义（本轮的主要修改）

### 2.1 结论有了**结构化结果**，不再从正文里猜

`conclusions` 新增 `conclusion_outcome` 列（纯 additive）。历史行留 NULL，读出来就是
`unknown`——**绝不**迁移成"无风险"。

真正的判断不靠这一列，而靠 `MemoryStore.evaluate_trigger(conclusion_id)`：从**依赖索引**
（`conclusion_dependencies`）与当前权威状态推出**本事项的触发条件**是否已经不成立。

| 依赖种类 | 触发条件 | 判定 |
|---|---|---|
| `medication_pair` | 两条药同时在用 | 任一条不再是 active 用药 → **已消除** |
| `medication` | 这条药在用 | 不在用 → **已消除** |
| `semantic_fact` | 那条事实仍按原值成立 | 事实被撤回或改写 → **已消除** |
| `medication_set` / `conclusion` | 只是"当时扫过整份列表" | 不足以单独证明 → **unknown** |

它只回答"本事项的触发条件"，**不**回答"整体用药是否安全"。

### 2.2 关闭必须现场证明，而不是"检查做过了"

`closure_evidence(case)` 逐条核对，缺一不可：

1. 关联结论仍 `current`，且其记录的输入版本等于**当前**版本；
2. 有结论表明本事项的触发条件**已消除**（上面的确定性判定）；
3. 关联结论里没有一条"触发条件仍然成立"的风险结论；
4. 没有阻塞性未决问题（`open` **或** `unknown` 状态都算）。

它的输出直接给界面（`GET /v1/safety-cases/{id}/closure-evidence`），所以"能不能关"
不是一个按钮说了算，用户能看到理由和阻塞项。

### 2.3 专业依据要过五道门

`_professional_basis` 逐条拒绝：不存在 / 未生效 / **动作不允许完成事项**（只有
`close_with_safe_guidance` 可以）/ **不是针对本事项作出的** / **决定作出后事实已移动** /
**来源是本地模拟工作台**。

最后一条是刻意的：本项目**没有连接真实医护服务**，把模拟工作台的决定包装成
"专业医疗确认"是这条路径上最危险的谎。

### 2.4 持续跟进不再伪装成"等待专业人员"

新增状态 `monitoring`（持续跟进中（风险仍在）），责任方是照护者，`next_action_summary`
明写"风险仍然存在…这不表示风险已经消除"。它记录的是**为什么不关闭**
（`resolution_basis.kind = 'monitoring_arrangement'`，带 `still_present` 与 `why_not_closed`），
不是一条关闭依据。

跟进安排必须可持久化：给不出可信时间/条件时记成 `confirmed: false` 的**待确认安排**，
模型不能自己编一个复查周期。一次例行 `sync` 也**不会**把它降级成"待调查"。

### 2.5 操作者身份来自认证上下文

`disposition` 的 `actor` / `roles` 由服务层的 principal 解析，**不读请求体的 `actor`**。
权限按（动作，依据）细分：以确定性检查关闭是照护者权限；以专业复核决定关闭**必须是
复核方自己的角色**。

## 3. Agent 拿到真正的事项上下文

`run_open_review(..., case_context=...)`——用的是**既有执行循环**，没有第三套引擎。

上下文每轮重新装入，随 investigation 状态持久化，`planner_view()` 里可见：

- `case` 事项身份与当前状态；
- `why` 触发原因 + 最近的状态/处置/补充事件（含**为什么**）；
- `subjects` 相关用药与事实（引用，不是副本）；
- `conclusions` 每条结论的 `state`、**`trigger_state`**、`version_applies`、`stale_reason`；
- `questions` 未决 / 用户明说不知道 / 已回答（带 `answer_kind`）；
- `existing_disposition`、`next_action_summary`、`responsible_party`；
- `previous_investigation` 上次做到哪（终止原因、检索、已读证据、开放缺口、claim 状态）；
- `new_since_last_run` 版本变化 + 上次之后收到的补充；
- `allowed_actions`、`budget`。

**默认只覆盖这一件事**：不铺开整个患者、不复述病史、不重读已有证据。要扩大范围是
Agent 自己的动作，且必须在 `purpose` 里给理由。

## 4. 决策是"有意义的下一步"，不是固定顺序

每次提案带五个结构化字段（不要求长篇推理）：`gap_id`（针对哪个未决问题）、
`basis_refs`（依据哪些已有结论/证据）、`tool` + `arguments`（动作与参数）、
`expected_observation`（预期解决什么）、`expected_change`（什么结果会改变下一步）。

`basis_refs` 缺省就是**空列表**——如实记录"没有援引依据"，界面显示"未说明"，
不替模型补一个它没给的理由。这些字段随决策进入运行轨迹。

## 5. 补问、回答与跨会话

三种"收到东西"分开处理，这是本轮的关键区分：

| 情况 | 请求状态 | 是否等用户 | 是否阻止关闭 |
|---|---|---|---|
| 有内容地回答 `provided` | `answered` | 否 | 否 |
| **明说不知道** `unknown` | `unknown` | **否**（改找替代证据） | **是**——不确定性没有消失 |
| 空值 `empty` | 保持 `open` | 是 | 是 |

补问必带 `why_needed`（"为什么需要这条信息，它会影响哪一步"），且只问用户答得上来的；
方向为专业复核的问题标成 `for_professional`，不由用户代答。

**跨会话**：`request_id` 由缺口派生（不含时间/序号），`require_input` 按 id 去重——
恢复后不会把同一件事再问一遍。反过来，**旧答案也不会永久挡住重新核对**：
回答记下当时的记录版本，事实一变该问题就被 `retire_stale_answers` 重新打开并写明原因
（历史里留 `answer_retired`，旧答案不被改写）。

**补充到达会经既有队列唤醒调查**：`POST /answer` 保存回答后，若同一事项确有一件
停在 `waiting_input` 的调查，就按现有的 `care_task` + outbox + 租约 + 预算那条路
把它排上——没有新的调度框架。唤醒是尽力而为，唤醒失败**不影响**刚保存的回答
（界面会如实显示"补充已存下、这轮还没能继续"）。等待用户输入期间不会反复调用模型：
只有补充到达或记录变化才会推进。

## 6. 界面

安全事项详情页补齐了闭环：为何出现 → 查到什么（含每条结论的**触发条件状态**）→
仍有什么不确定 → 现在需要我做什么（带 `why_needed` 的单题回答）→ 补充之后发生了什么变化。
补充失败保留输入、显示服务端原文，不要求重填。

必要检查的结果与 Agent 的调查贡献分开显示；工具轨迹与预算收进可展开区，不占主流程。
关闭面板先读 `closure-evidence`，只提供服务端会接受的动作；拒绝理由原样展示。
