# 长期用药回访 Agent（2026-09-14）

**基线**：`integration/parallel-delivery` @ `9e36d30`（上一轮已验收的集成版本）
**分支**：`feat/review-visit`
**工作方式**：单 Agent 串行；不启子 Agent、不并行跑测试、不建多组服务；
所有测试与脚本使用 `output/visit/` 下的隔离临时库，端口避开 8000/5173。
**原工作区与集成分支全程未动。**

---

## 一、用户现在能完成的新事情

打开一件事项，点详情页上的「**开始回访**」（已经有没结束的回访时是「**继续本次
跟进**」），进入 `/safety/:caseId/visit`，按五步看到：

1. **这次为什么需要跟进** —— 到期 / 相关记录变化 / 收到新补充 / 您主动发起。
   服务端**按事实判定**，不是调用方自报；进入页面就能看到，不必先"开始"。
2. **上次之后已记录的变化** —— 用持久化游标（上次回访结束的位置）算，不是"最后几条"。
   没有新记录时只说「系统尚未收到新记录；这不等于情况没有变化，也不表示风险已经解除」。
3. **当前最需要回答的问题** —— 最多 1～3 条；信息已经足够时**不硬造问题**。
   每条都能回答五种表态：**已完成 / 尚未完成 / 不清楚 / 情况有变化 / 暂不回答**。
4. **回答之后的实际进展**。
5. **本次结果及下一次安排** —— 含安排**是否已被确认**（"已安排"≠"已确认"）。

用药有变化时，登记一条**待确认的变更候选**（自己填，或模型从您的话里读出来——
两种来源在界面上分得开）。**确认之前当前药单一个字节都不动**；确认后走既有的
用药变更入口写入，必要安全检查按原有路径重新排队。

中途离开再回来，回到同一个 URL 就是**同一次**回访：已提交的回答还在，从停下那步继续。

## 三、集成阶段（上一轮）后本轮又修掉的**自己引入的**缺陷

四处都是"跑起来才暴露"：

1. **工具层的中文引号写成了 ASCII 引号** → `default_tools.py` 语法错误。
   离得很远的后果：确定性重查捕获了导入失败、记成 `status: error`，结论永远拿不到
   后继版本 → 关闭事项报「依据结论已失效」——**用户关不掉本来就该能关的事项**。
   由 `test_safety_cases` 抓到。**改完工具文件先 `ast.parse`。**
2. **推迟类回答唤醒调查 → 那一轮必然熔断**。这三种回答保持问题未决，而完成条件在
   「有新信息没看过」时不终止；唯一未决的问题若是 `ask_user`，模型没有合法动作 →
   重复被拒 → `unrecoverable_failure`。用户会看到「这次回访没有跑成」，而他只是说了
   一句「还没做」。修法：**推迟类不唤醒**，**候选确认之后才唤醒**。
3. **幂等键第三次踩同一类坑**：`save_result` 的 payload 不含结果内容 → 第二次保存
   直接命中第一次的回执，**新结果被静默丢弃**（用户确认了候选，却读不到"这次改变了
   什么"）。规则：**payload 可能不同，键就必须带判别项**。
4. 需求第七条说"进入后依次看到的第一件事是为什么跟进"，但原来要先点"开始回访"
   才看得见——补了只读的 `next_visit_reason` 预览。

## 四、验证

### 4.1 离线（脚本化规划器，**不调模型**）

三个产品场景，走真实 HTTP 端点 + 真实 worker：

| 场景 | 断言 | 结果 |
|---|---|---|
| **A 已有信息充分** | 复用已有答案、**不产生新补问**、结果看得出复用 | 通过 |
| **B 出现相关变化** | 识别缺口→提问→「情况有变化」→候选→**确认前记录不变**→确认→记录更新→**必要检查重新排队**→同一事项→结果里说清改了什么 | 通过 |
| **C 跟进行动未完成** | 「尚未完成」保留未决、事项不解决、仍挡住关闭；「已完成」只对跟进行动类问题成立；「不清楚」转替代证据；「暂不回答」≠「不知道」 | 通过 |

另加：候选未确认不改记录（有断言）、同字段只留一条待确认、模型工具只产生候选、
三处字段清单一致（工具 schema / 调查校验 / 确认写入）。

## 五、未完成项与实际限制

1. **真实模型未通过**（§4.4）。回访的三个产品场景全部由**脚本化规划器**验证——
   它验的是状态与恢复机制，**不能**记成真实 Agent 自主成功。
2. **真实用量未测到**（脚本记账缺陷，§4.4）。
3. **`assessment` 在真实批次里的分布**仍未测（沿用上一轮的未完成项）。
4. **`retire_stale_answers` 与依赖协调器仍是两个入口**：前者按 `answered_against`
   重开**请求**，后者让答案的 `assessment` 降到 `stale`/`unsupported`。契约 §3.6
   "重开时 assessment 应变为 stale"只在 on_event 触发那条路上接上了。
5. **上一轮的两条 O-1/O-2 仍未修**（项目默认离线闸门因此是红的，上一轮已记录）。
6. **候选变更的写入通道只覆盖 `dose`/`schedule`/`route`/`start_at`**：停药、换药
   （add/remove）还没有候选形态——它们在既有入口里本来就是显式操作，本轮没扩。
7. **"个人提醒"与"专业复查安排"的区分**沿用既有 `owner` 渲染，本轮未新增校验。
8. **跨事项的"同一事实复用已有答案"只通过权威记录发生。** 已被确认进记录的事实，
   另一件事项可以用 `source='patient_record'` 直接复用（`answer_question` 本来就支持）；
   而**未确认的用户口述不会跨事项共享**——把它当事实复用，等于让一句没核对过的话
   在两件事项上同时生效。这是**刻意**的取舍，不是漏做。不同对象的问题也不会被合并：
   `question_id` 由（信息目标 × 对象 × 字段）派生，`answer_question` 另有对象错配的
   拒绝路径（既有测试覆盖）。
9. **"不得凭模型自行生成临床阈值或检查周期"只做到结构性约束，没有做内容检查。**
   结构性那一半是成立的：模型**没有**任何能把阈值或复查周期写进记录的权限——
   它不能写用药记录，变更候选必须由用户确认，也没给它排下一次安排的工具。
   但它仍可能在**问题的措辞**里提到一个阈值（例如"每 3 个月复查一次吗？"），
   本轮**没有**对这种措辞做机械检查，也没有为此写断言。这是一处**已知的、
   未实现的**护栏，不要读成"已经守住了"。
