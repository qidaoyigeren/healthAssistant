## 一、用户行为的改善

**同一件安全事项的第二次回访，现在与第一次不一样了。**

在此之前，每一次回访都是从头开始：模型拿到的是同一句"请核实该风险在当前记录下
是否成立"，看不到上次做过什么、上次之后来了什么、自己上次的结论还算不算数。
于是"回来继续跟进"实际上等于"把第一次重做一遍"，而用户被反复问同样的问题。

现在：

1. **系统记得上次做过的事。** 第二次回访开工时，模型面前摆着上一次的结果——它
   当时留下了什么没解决、结论是什么、什么时候收的尾；以及上次之后就位的、仍有效
   的答案（连同值、来源和可信性判定）。已有的结论**直接沿用**，不再要求重新证明。
2. **只围绕真正变化的部分继续。** 上次之后实际发生的事件与变化的记录范围单独列出；
   期间没有任何新信息时，页面说的是「系统尚未收到新记录；这不等于情况没有变化，
   也不表示风险已经解除」——**没有新记录 ≠ 情况稳定**，这两句话从措辞上就分开。
3. **受影响的重核，不受影响的不动。** 记录变化只把**真正依赖那个范围**的回答标成
   需要重新核对，不再把所有问过的问题重开一遍。用户回来一次不必重答一遍。
4. **本次为什么结束，说清楚。** 结束与等待分开讲：「本次没有新的变化，已有结论
   仍然有效，因此结束」／「本次在等您补充：…」／「本次回访没有跑成：…」。
   等待不再冒充结论。
5. **每条关键内容都带来源。** 程序的核对、用户的报告、模型的解释、权威记录，
   在界面上分得开。
6. **"没做完"可以接着说。** 「还没做，下周一开始」里有一个新时间，系统据此继续；
   一句干巴巴的「还没做」则正常等待，不空转、也不重复追问。

**判据**：同一件安全事项第二次回访时，系统能够利用第一次的结果和期间变化，
执行有区别、有依据的下一步。

## 三、两处前置边界修复（O-1 / O-2）

这两条是上一轮记录的基线缺陷，直接破坏"答案复用"，本轮必须处理。

- **O-1 共享药名不再等于共享主题。** 支持判定原来只查实体名与数字，从不看**谓语**，
  于是一段讲出血风险的文字会把「服药频次是什么」读成已有依据。现在还要问片段有没有
  谈到问题所问的那个属性（属性词表优先，无字段时退回内容词），材料路径不受影响。
- **O-2「已有依据」必须能指认是什么回答了它。** 原来问题被写成 `available` 却
  **不写答案元素**——界面只能显示"已回答"，显示不出回答是什么。现在回读时记下命中
  支持的片段，据此写出答案元素（来源 + 引文 + 既有 assessment）；指不出片段就不
  settle。

**这两条修好之后，项目默认的离线闸门第一次全绿。**

### 4.4 真实运行发现、离线没能发现的缺陷

第二次回访的摘要说「没有范围变化、没有事件」，而**期间明明加了一味药**。两个原因：

1. 摘要拿事项自己的 `input_versions` 当基线，而那次改动顺手把它刷新了——
   变化把自己的证据抹掉了。现在回访在**开始时记下记录版本**，下一次跟它比。
2. 上一次回访没落 `after`（例如它被阻塞）时，起点退回 **0**，等于把整件事项的
   来龙去脉当成"上次之后"重报一遍。现在退回**它开始的位置**。

两条修复都有离线断言，且**对真实运行实际跑过的代码是失败的**——是修复，不是描述。

## 五、未完成项与实际限制

1. **真实模型未通过**（§4.3）。本轮所有"利用上次结果"的行为由**脚本化规划器**验证，
   **不能**记成真实模型自主成功。
2. **修复晚于真实运行。** §4.4 的两条是在那次真实运行**之后**修的，只有离线验证。
   结论是"能看见变化了"，不是"真实模型据此改变了下一步"——后者仍未测到。
3. **`changed_scopes` 仍是较弱的一路信号。** 它比的是版本号，能说明"变了哪一类"，
   说不出"具体变在哪一条"；具体变化由游标之后的事件承担。两者不可互换。
4. **"带可消费信息才唤醒"是词法启发式**：只认日期、带单位的量值与相对时间词。
   改写过的说法（"改成每天两次了"）认不出来，错误方向是**少唤醒**。有断言钉住
   这条边界，不是漏做。
5. **`assessment` 在真实批次里的分布**仍未测（沿用上一轮的未完成项）。
6. **候选变更的写入通道**仍只覆盖 `dose`/`schedule`/`route`/`start_at`。
7. **"不得凭模型自行生成临床阈值或检查周期"**仍只有结构性约束，没有对问题措辞的
   机械检查（沿用上一轮）。

## 一、用户现在能完成的新事情

打开一件事项，点详情页上的「**开始回访**」（已经有没结束的回访时是「**继续本次
跟进**」），进入 `/safety/:caseId/visit`，按五步看到：

1. **这次为什么需要跟进** —— 到期 / 相关记录变化 / 收到新补充 / 您主动发起。
   服务端**按事实判定**，不是调用方自报；进入页面就能看到，不必先"开始"。
2. **上次之后已记录的变化** —— 用持久化游标（上次回访结束的位置）算，不是"最后几条"。
   没有新记录时只说「系统尚未收到新记录；这不等于情况没有变化，也不表示风险已经解除」。
3. **当前最需要回答的问题** —— 最多 1～3 条；信息已经足够时**不硬造问题**。
   每条都能回答五种表态：**已完成 / 尚未完成 / 不清楚 / 情况有变化 / 暂不回答**。
4. **回答之后的实际进展**。
5. **本次结果及下一次安排** —— 含安排**是否已被确认**（"已安排"≠"已确认"）。

用药有变化时，登记一条**待确认的变更候选**（自己填，或模型从您的话里读出来——
两种来源在界面上分得开）。**确认之前当前药单一个字节都不动**；确认后走既有的
用药变更入口写入，必要安全检查按原有路径重新排队。

中途离开再回来，回到同一个 URL 就是**同一次**回访：已提交的回答还在，从停下那步继续。

## 三、集成阶段（上一轮）后本轮又修掉的**自己引入的**缺陷

四处都是"跑起来才暴露"：

1. **工具层的中文引号写成了 ASCII 引号** → `default_tools.py` 语法错误。
   离得很远的后果：确定性重查捕获了导入失败、记成 `status: error`，结论永远拿不到
   后继版本 → 关闭事项报「依据结论已失效」——**用户关不掉本来就该能关的事项**。
   由 `test_safety_cases` 抓到。**改完工具文件先 `ast.parse`。**
2. **推迟类回答唤醒调查 → 那一轮必然熔断**。这三种回答保持问题未决，而完成条件在
   「有新信息没看过」时不终止；唯一未决的问题若是 `ask_user`，模型没有合法动作 →
   重复被拒 → `unrecoverable_failure`。用户会看到「这次回访没有跑成」，而他只是说了
   一句「还没做」。修法：**推迟类不唤醒**，**候选确认之后才唤醒**。
3. **幂等键第三次踩同一类坑**：`save_result` 的 payload 不含结果内容 → 第二次保存
   直接命中第一次的回执，**新结果被静默丢弃**（用户确认了候选，却读不到"这次改变了
   什么"）。规则：**payload 可能不同，键就必须带判别项**。
4. 需求第七条说"进入后依次看到的第一件事是为什么跟进"，但原来要先点"开始回访"
   才看得见——补了只读的 `next_visit_reason` 预览。

  没有走到"提问 → 用户回答 → 下一步变化"那一段，所以第九节的**后三项未测到**：
  是否复用已有信息、是否随回答改变下一步、是否形成具体带来源的结果。
- 失败后**没有**追加批次、换模型或扩大预算。

> **用量数字不可引用**：报告里的 `calls_actual` / `tokens_actual` 记成 0，与"确实发生了
> 模型调用"矛盾——记账没读到该读的地方。这是**验收脚本的测量缺陷**，不是产品行为。
> 下一轮应先修这个读数，再谈预算结论。

**工程机制通过 ≠ 模型能力通过。** 本轮的模型能力结论是：**未通过**。

## 五、未完成项与实际限制

1. **真实模型未通过**（§4.4）。回访的三个产品场景全部由**脚本化规划器**验证——
   它验的是状态与恢复机制，**不能**记成真实 Agent 自主成功。
2. **真实用量未测到**（脚本记账缺陷，§4.4）。
3. **`assessment` 在真实批次里的分布**仍未测（沿用上一轮的未完成项）。
4. **`retire_stale_answers` 与依赖协调器仍是两个入口**：前者按 `answered_against`
   重开**请求**，后者让答案的 `assessment` 降到 `stale`/`unsupported`。契约 §3.6
   "重开时 assessment 应变为 stale"只在 on_event 触发那条路上接上了。
5. **上一轮的两条 O-1/O-2 仍未修**（项目默认离线闸门因此是红的，上一轮已记录）。
6. **候选变更的写入通道只覆盖 `dose`/`schedule`/`route`/`start_at`**：停药、换药
   （add/remove）还没有候选形态——它们在既有入口里本来就是显式操作，本轮没扩。
7. **"个人提醒"与"专业复查安排"的区分**沿用既有 `owner` 渲染，本轮未新增校验。
8. **跨事项的"同一事实复用已有答案"只通过权威记录发生。** 已被确认进记录的事实，
   另一件事项可以用 `source='patient_record'` 直接复用（`answer_question` 本来就支持）；
   而**未确认的用户口述不会跨事项共享**——把它当事实复用，等于让一句没核对过的话
   在两件事项上同时生效。这是**刻意**的取舍，不是漏做。不同对象的问题也不会被合并：
   `question_id` 由（信息目标 × 对象 × 字段）派生，`answer_question` 另有对象错配的
   拒绝路径（既有测试覆盖）。
9. **"不得凭模型自行生成临床阈值或检查周期"只做到结构性约束，没有做内容检查。**
   结构性那一半是成立的：模型**没有**任何能把阈值或复查周期写进记录的权限——
   它不能写用药记录，变更候选必须由用户确认，也没给它排下一次安排的工具。
   但它仍可能在**问题的措辞**里提到一个阈值（例如"每 3 个月复查一次吗？"），
   本轮**没有**对这种措辞做机械检查，也没有为此写断言。这是一处**已知的、
   未实现的**护栏，不要读成"已经守住了"。
