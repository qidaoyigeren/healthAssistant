## 一、用户现在可以用什么自然表达完成操作

在回访页的「**补充情况**」里直接用自己的一句话：

| 用户说 | 系统做什么 |
|---|---|
| "合成药甲改成每天两次了" | 生成一条**调整用法**候选（中文数字照收，没有阿拉伯数字不算"没信息"） |
| "上周已经停了合成药甲" | 生成一条**停用**候选；"上周"保留原话，**不**解析成某一天 |
| "开始吃合成药丙了，2mg" | 生成一条**新增**候选 |
| "合成药甲又接着吃了" | 生成一条**恢复服用**候选，指向那条具体的停用记录 |
| "之前登记停用是填错了" | 生成一条**纠正记录**候选，回到原来那个服用阶段 |
| "合成药甲换成合成药丙了" | 生成**一组**两条候选（换出 / 换入），可整组一次性确认 |
| "打算下周停药甲" | **不进**可确认列表，落成"您提到但还没发生的事" |
| "药甲要不要停" | 同样不生成候选（那是一个问题，不是一次变化） |
| "昨天漏了一次" | 记成一条用户报告，**不改**药单 |
| "这个药改了"（说不清是哪个） | **补问**："您说的是哪一种药？"，不猜 |

确认弹出来的候选之前，**权威药单一个字节都不动**。

## 二、四类意图怎么分开

每个操作**各自**带一个"这是在说什么"，不用一句话的总体语气代替：

* **实际发生**（`occurred`）→ 生成可确认候选；
* **计划**（`planned`）→ 落成计划记录，**不进**可确认列表；
* **询问**（`question`）→ 什么都不生成；
* **漏服**（`missed_dose`）→ 记成用户报告，不改药单；
* **纠错**（`correction`）→ 生成纠正候选，并**撤回**被否定的那条待确认候选。

"旧药已经停了，新药打算明天开始"会得到**两条**操作：一条已发生的停用、一条计划中的新增。
不用一个全局 intent 把其中一半丢掉。

**"不是药甲，是药乙"不会改动药甲**：被否定的那条待确认候选被撤回（保留历史与
"被谁取代"的指向），药甲记录一个字节不变。

## 三、换药与恢复怎么保留历史

三件事**分开表达**，谁也不从谁的 `status` 反推：

| | 载体 | 含义 |
|---|---|---|
| 记录版本关系 | `predecessor_id` | 哪一版取代了哪一版 |
| 真实服用阶段 | `episode_id` | 患者**连续服用**的那一段（写入时定死，永不重算） |
| 纠错关系 | `corrects_id` | 这一行在撤回哪一条记录 |

* **真实停用后恢复** → 新阶段，并把 `predecessor_id` 指回那条停用记录；
* **误登记停用的纠正** → 继承被纠正行的 `episode_id`，回到**原来那一段**，
  而原错误记录**原样保留**（它确实被登记成停用过），靠 `corrects_id` 互相指向；
* **已有真实恢复记录时纠正旧记录** → **拒绝写入**并如实报冲突。不自动作废那段
  真实用药史——那等于用一次历史纠错抹掉一段真实记录。

**为什么不用"把旧行改成 superseded 再重算阶段"**：`episode_anchor` 的输出已经被
持久化进事项的 `dedup_key`，而按可变 `status` 重算**不会回头修正那些 key**。迁移把
历史行回填成**当时**那个算法的输出，所以存量事项的身份逐字节不变（有断言）。

## 四、确认之后怎么接上

一条链，没有第二套：

```
确认候选 → apply_confirmed_medication_candidates（**唯一**入口）
        → memory._apply_medication_change_tx（带 expect={记录ID,版本,状态,作用域}）
        → 权威表 + 必要检查登记 + 候选落定 + 成功回执  ← 同一个事务
        → 重渲染回访结果 → 唤醒这一次回访 → 继续
```

* **必要检查**按药单**版本**去重登记；`safety_checks` 本来就是按**当前全部在用药**
  重扫，不是只查被换的那两种（本轮补的是断言，不是重建）；
* **旧结论不能批准新记录**：药单一动，结论的 `input_revision` 就对不上，关闭被挡下；
* **停药不等于风险解除**：`closure_evidence` 新增 `nature`，显式区分
  "本事项的触发条件在当前记录下不再出现"与"整体风险已解除"——后者这一位恒为
  `false`，系统从不做这个判断。未决问题仍阻止关闭。

## 五、幂等与冲突：不把两件事混成一句

| 情形 | 行为 |
|---|---|
| 同一个 key、同一请求重放（超时重试） | **返回原有成功回执** |
| 同一个 key、不同内容 | 409 |
| 另一个请求撞上已处理的候选 | 明确的冲突 |
| 记录已变（版本 / 状态 / 归属不符） | 拒绝写入，冲突**在另一个事务里落盘**，所以 409 之后它仍在、刷新仍在 |
| A→B→A（值回到原样、版本已变） | 仍判过期——只比字段值会把它放过去 |

**候选创建的身份**包含来源（补充记录的哪一次解释，或调用方的 key）、操作、目标与
内容摘要；只追加 `before` 值分不开"撤销后重新声明 / 同值不同版本 / 重新解释"。

**受控写入没有被放宽**：`record_input` 继续拒绝 `remove`。普通补充回答不能靠加一个
`action='remove'` 绕过候选确认；请求体里的 `confirmed` 一律不读。

## 六、已验证的行为

### 离线（`stage0/test_medication_change_flow.py`，39 个用例）

真实 HTTP 端点 + 真实 worker + 隔离库，**从真实候选与确认入口进入**，不直接写库
制造通过。脚本化的是理解器的**措辞**，机制一步没省。

覆盖：新增进入记录并触发必要检查 ｜ 停用前后记录与历史（含"未知停药时间不写 now"）｜
恢复形成新阶段并链接指定停用记录 ｜ 纠错回到原阶段且原记录可追溯 ｜ 已有后继真实记录时
纠错被拒且零写入 ｜ 换药部分完成的逐条陈述 ｜ 计划/询问/漏服三条对照都不改药单 ｜
指代不明补问 ｜ 原文依据对不上就不采信 ｜ 中文数字 ｜ 版本冲突不覆盖 ｜ A→B→A 仍过期 ｜
同 key 重放返回原回执 ｜ **重试按两次只算一次调用** ｜ 改过的候选不会在重启后复活 ｜ 模型无配置/失败都保留原文并可显式重试 ｜
空输入被拒 ｜ 确定性按钮不调模型 ｜ 普通回答不能停用一个药 ｜ 未知动作仍被拒 ｜
换药整组故障注入后零半组 ｜ **迁移不变式**（回填后阶段锚点与迁移前逐字节相同）｜
停药不被当成风险解除 ｜ 未决问题阻止关闭 ｜ 旧结论不能批准新记录。

### 浏览器（`scripts/review-visit-browser-acceptance.js`，36/36 步通过）

带歧义的换药：自然描述 → 补问 → 查看候选 → 修正 → 确认 → 查看当前记录、历史与
安全检查状态。另含原有的回访五步、来源属性、刷新后仍在同一次回访。

### 离线闸门

`scripts/verify-agent-closeout.py`：57 个套件 / 1092 个测试，全部通过；
主线六个类别全过。（本轮同时**关掉了一个基线自带的红**：回访序号原来按
`opened_at` 排序数，同一秒内的两次回访由随机 uuid 决定先后，"第几次回访"会数错。）

## 七、有限真实验收：**四个结论分开报告**

场景：一次连贯的换药登记，其中一次对象说不清。
**开跑前声明上限：4 次调用 / 40k tokens / 180 秒**，先到先停，不追加批次、不换模型。

| 结论 | 结果 |
|---|---|
| **1 自然语言理解** | **通过**（就第 1 句而言） |
| **2 候选确认与原子写入** | **未走到**——真实模型那一轮没有形成候选 |
| **3 用药阶段与纠错历史** | **未走到**（同上；离线用例已覆盖） |
| **4 安全事项与回访承接** | **未走到**（同上；离线用例已覆盖） |

**一项通过不等于整个流程完成。** 下面写清楚每一项到底发生了什么。

**第 1 句**"这个药不吃了，换成另一种了" → 模型输出
`operation=remove, drug_quote="这个药", uncertain=["object_ambiguous"]`，
并自己提问"**您说的是哪一种药？**"——**没有编一个药名**。这正是需求要的行为
（"指代只有在上下文能唯一确定对象时才关联"），记为通过。用量 1688 tokens（实测）。

**第 2 句**"是合成药甲，上周就停了；换成合成药丙，明天开始" → 模型**自相矛盾**：
`drug_name="合成药甲"`、`drug_quote="合成药甲"`，却同时标了 `object_ambiguous`。
我的代码照抄了它，于是候选被挡下，后面三项都没走到。

**这条已经修掉**：歧义改由**能不能唯一解析到一条权威记录**判定——名称就出现在模型
自己给出的依据片段里时，那是点名不是指代，标记去掉；指代保留歧义、照样补问。
另修：时间含糊（"上周"）本来就可表达（`reported_vague`），不该阻塞候选。
两条都有离线回归用例（`AmbiguityFlagTests`）。

**没有为了追一个通过再花一次真实调用。** 真实调用合计 **5 次**（1 次探针 + 2 次
被我自己脚本 bug 中断的批次 + 2 次有效批次），**超过声明的 4 次**——超出的部分来自
我的工具缺陷与场景措辞返工，不是模型重试。token 合计约 4.3k，远低于 40k 上限。

**记账本身也修了一个真缺陷**：这次理解先前没有自己的运行记录，`budget_scope` 会
直接拒绝发起调用——而**脚本化解释器把这条路径整个盖住了**（离线测试从不真正调用
`read()`）。现在它有自己的运行记录，预算、尝试台账与用量都进既有那本账。

> **存档里的一个自我更正。** `output/medchange-live-2/` 与 `-3/` 的 JSON 里，
> `history` 与 `continuity` 两项写着 `passed: true`——那是**空的**：这一轮一次记录
> 都没改，于是"没有伪造的停药时间""事项没有被自动清除"两句自动成立。空过的通过
> 不是证据。脚本已改成在没有任何确认写入时如实记 `passed: false` + "没有被走到"；
> 上面那张表按更正后的口径写。存档不删——失败证据不能被新结果顶掉。

## 八、尚不支持的边界

1. **真实模型的"计划 / 已发生"区分没有跑通验证**。第 2 句被模型标成两半都是计划——
   有一种读法说得通（"换成 B，明天开始"统辖整句），但**没有**验证到它能把
   "已经停了"与"明天开始"分开。
2. **一次换药跨两次提交会形成两个组**。同一句话里说的算一组，可以整组原子确认；
   分两句说则各成一组，只能分别确认，或靠候选合并（同一味药同一件事会合并）对齐。
   界面会显示各自属于哪一组。
3. **对象纠正只覆盖"否定 + 改口"这一种**。"我之前说的那个药名记错了"这类需要
   重新解析名称的说法没有专门路径。
4. **`time_text` 只保留用户的原话**，没有结构化成区间。
5. **纠错只覆盖"误登记停用"**。"之前登记的剂量填错了"要走普通调整；
   "之前登记的恢复记录是错的"没有专门路径，会与真实记录冲突而拒绝。
6. **停药之后的关闭路径**：触发条件客观消除时，按**既有**依据规则仍然可以处置关闭。
   本轮**没有**改这个规则（需求要求沿用），只把"触发条件不再出现"与"整体风险已解除"
   在表达上分开，并让 `nature` 恒不主张后者。
7. **`medication_change_unresolved` 仍然只写事件不写记录**（既有的降级行为）；
   候选路径已经不会走到它——走不到就报冲突。

## 九、本轮改到的既有行为

* `medications` 新增 5 列（`episode_id` / `operation` / `corrects_id` /
  `end_at_basis` / `time_text`），**additive only**，历史行按当时算法回填；
* `MemoryStore._apply_medication_change_tx` 支持 `resume` / `correction` 与
  `expect` 前置核对；既有路径（`expect=None`）行为不变；
* `CareTasks.record_input` **仍然拒绝** `remove`；新增
  `apply_confirmed_medication_candidates` 作为唯一接受已确认候选的入口；
* `_ensure_visit_task` 的创建幂等键改为按"这次回访的第几件任务"（原先只用 focus
  长度，焦点没变而上一件已收尾时键完全相同、payload 不同，`command` 直接判成
  "同一标识用于不同内容"报 409）；
* `ReviewVisitStore.for_case` 的排序不再承担"第几次"的语义——序号在创建时写死；
* `ProductStore.receipt()` 新增，用来把"重放"与"冲突"分开。
